# 非空接口转换只依赖可能被动态调用的方法

## 背景与问题

[ADR-0001](0001-interface-conversion-contracts.md) 让每个接口转换点依赖被转换类型的完整契约：全部方法、字段布局和嵌套命名类型的契约。

在多服务的 monorepo 中，这会集中产生一类多报：同一个 API client 被注入到很多服务，各服务的工厂都把它转换为 client 包的接口。client 新增或修改一个方法时，即使大多数服务从不调用它，所有做转换的工厂都依赖完整契约，于是所有注入该 client 的服务都被报出。链接器符号检查显示，这些 binary 只是因为接口方法表保留了该方法，服务代码并不调用它。

## 决策驱动因素

- 结果用于 CI 选择构建和部署，漏报的代价仍高于多报，不能为减少多报引入常见场景的漏报。
- 保持 ADR-0001 的线性复杂度，不重新引入值流追踪。
- 只使用 `go/types`、已有的 SSA 结果和声明依赖图，不加载依赖库源码。

## 考虑过的方案

- A：保持完整契约。
- B'：分派契约，全局按方法名和签名判断可达：任意位置有同名同签名的接口调用，方法就进入分派契约。
- B：同 B'，但只统计类型实现了的接口，用 `types.Implements` 判断。
- C：按值流求交。追踪接口值能流到的调用点，只有能拿到这个转换产生的值的调用点调用了方法，转换点才依赖它。
- E：在 B 的基础上，对只由本地代码经接口调用的方法，要求转换点和调用点在同一个 package 汇合。
- D：`error` 转换也使用分派契约。

## 决策结果

选择 E：

- 转换为 `any` 和 `error`（以及实现了 `error` 的接口）仍用完整契约。
- 转换为其他非空接口时依赖分派契约：字段布局和“任意位置”可能调用的方法。任意位置包括类型断言和 type switch 检查的接口、依赖库导出的接口，以及标准库用匿名接口检查的 `Unwrap`、`Is`、`As`、`Timeout`、`Temporary`。所有接口都要求类型实现它。
- 只由本地代码经接口调用的方法作为分派契约的条件依赖，记录发起调用的声明；接口可以是本地声明的、匿名的或函数内定义的。分析时，这样的方法受影响后，只标记同时有声明到达转换点（分派契约的反向闭包）、也有声明到达调用点（调用方声明及其反向闭包）的 package 中的这些声明，不再沿普通依赖继续扩散。接口里声明了但没有代码经接口调用的方法，既不进入分派契约，也没有条件依赖。

按 package 汇合而不是按声明汇合，是因为包初始化和 `main` 是同一个 binary 中互不引用的声明：插件在 `init` 里注册、`main` 里调用时，没有任何单个声明同时到达两边。

B' 在客户端与服务端接口同名同签名时仍有多报：服务端经服务接口的调用会让签名相同的客户端方法变成可达。经 J 的调用只会分派到实现了 J 的类型，B 的实现关系检查是可靠的收窄。B 仍保留全局可达：只要有一个服务经接口调用了某个客户端方法，所有注入该客户端的服务都依赖它；E 的汇合消除了这部分。

C 需要值流或调用图分析，正是 ADR-0001 否定的方向。D 会漏掉依赖库通过匿名接口检查的错误方法，例如 `pkg/errors` 的 `Cause()` 和 gRPC 的 `GRPCStatus()`，这些检查写在依赖库函数体里，export data 看不到。

### 正面影响

- 没有代码经接口调用的新增或修改方法，只报出方法所在 package。
- 经接口调用的方法，只影响同时转换该类型并执行调用的 binary，不再扩散到所有注入同一客户端的服务。
- 类型断言、type switch、`fmt.Stringer`、`json.Marshaler`、`http.Handler`、`errors.Unwrap`、包初始化注册等场景仍然传播。回归用例见 `internal/impact/interface_flow_test.go` 中的 `TestAnalyzeIgnoresAddedMethodWithoutDynamicCaller`、`TestAnalyzeIgnoresMethodNeverCalledThroughInterface`、`TestAnalyzeIgnoresSameMethodOfInterfaceTypeDoesNotImplement`、`TestAnalyzeReportsOnlyBinariesThatCallChangedMethod`、`TestAnalyzeReportsOnlyBinariesThatCallThroughAnonymousInterface`。

### 负面影响

- 只做转换、或只做调用的 package 不再报出，只报出两者汇合的 package（通常是 binary 的 main 或装配代码）。按 package 选择测试时，测试需要用 `-tests` 分析，测试代码里的调用才会让被测 package 汇合。
- 值先转换为非 `error` 的非空接口，之后再按方法名反射调用（例如模板 `{{.Method}}` 渲染接口字段），或被依赖库用未导出、匿名接口检查名单以外的方法时，这些方法不在分派契约内，会漏报。
- 汇合按 package 判断：同一 package 中分别到达转换点和调用点、但从不在同一执行中组合的代码，仍会被报出。
- 依赖库导出接口会让一些方法在任意位置可达，例如实现了 `io.Closer` 的类型的 `Close`。
- 转换为 `any` 使用完整契约：类型新增一个方法，即使只经 `encoding/json` 解码使用、从不被调用，解码它的代码也会被报出。
- 泛型类型的方法和提及类型参数的接口在实例化前无法判断实现关系，按方法名匹配。
- 每个命名类型多一个 dispatch symbol，分析时要为触发的条件依赖计算反向闭包。

## 各方案取舍

### A：保持完整契约

- 优点：不会因为动态调用识别不全而漏报。
- 缺点：方法很多、被广泛注入的类型（例如 API client），每次新增或修改方法都会报出所有注入它的服务，CI 的服务选择失去意义。

### B'：只按方法名和签名匹配

- 优点：实现最简单，不需要做实现关系检查。
- 缺点：客户端和服务端接口常用相同的方法名和签名，服务端的调用会让客户端方法变成可达。

### B：实现关系检查、全局可达

- 优点：可靠地排除不实现调用接口的类型，仍只依赖类型信息。
- 缺点：一个服务调用了客户端方法，所有注入同一客户端的服务都被报出。

### C：按值流求交

- 优点：精度最高。
- 缺点：需要追踪接口值到调用点的流向，复杂度和漏报风险回到 ADR-0001 之前的状态。

### D：`error` 也用分派契约

- 优点：错误类型新增方法时多报更少。
- 缺点：错误值是依赖库最常用匿名接口检查的对象，漏报风险高；错误类型的方法通常很少，完整契约带来的多报有限。
